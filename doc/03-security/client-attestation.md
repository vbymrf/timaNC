# Аттестация клиентов

> Задача: сервер принимает чувствительные запросы только от неизменённого официального приложения на реальном устройстве. Без аттестации остальная защита обесценивается (левый клиент может честно говорить по протоколу).  
> См. также: [client-hardening.md](./client-hardening.md), [key-lifecycle.md](./key-lifecycle.md) §10, [24-device-linking.md](../doc_UI/24-device-linking.md).

## 1. Матрица

| Платформа | Механизм | Что доказывает |
|-----------|----------|----------------|
| iOS | **App Attest** (DeviceCheck) | Запрос от неизменённого бинарника на реальном Apple-устройстве |
| Android | **Play Integrity API** | Легальное Android-устройство; приложение из Google Play / подписано нами |
| Windows | **QR-привязка через телефон** | Доверие производно от аттестованного мобильного устройства ([key-lifecycle.md](./key-lifecycle.md) §10) |

Windows аппаратно не аттестуется — телефон служит якорем доверия. Web не входит в release scope и потребует отдельного trust-model решения.

## 2. Интеграция в KMP

```kotlin
// commonMain
interface AttestationProvider {
    suspend fun getAttestationToken(action: String): String
}
// iosMain     → DCAppAttestService: генерация ключа при первом входе, подпись хеша запроса
// androidMain → Play Integrity: prepare при старте, request при важных вызовах
// desktopMain → LinkedDeviceProvider: подписанный телефоном линк-сертификат
```

**Бэкенд:** канонические эндпоинты `POST /v1/verify/attestation/ios` и `POST /v1/verify/integrity/android` — верификация через Apple/Google API, результат кэшируется на устройство (TTL 24 ч, Redis). Аттестация требуется при регистрации, привязке устройства, смене ключей и массовых операциях. Не на каждый запрос (латентность/квоты).

## 3. Защита API помимо аттестации

| Что | Как |
|-----|-----|
| Отличить клиент от скрипта | HMAC-подпись запросов (ключ обфусцирован в клиенте; ротация каждые 2 недели через force update) |
| Украденные ключи/токены | Rate limiting per device/user (Redis), мониторинг аномалий |
| Секреты третьих сторон | Не хранятся в клиенте вообще — только backend-proxy |
| Ключ локальной БД | Производный от пароля пользователя + привязка к устройству |

**Золотое правило:** считаем, что любые ключи из клиента будут извлечены. Значит: чувствительное — на сервере, лимиты — на сервере, ротация — регулярная, мониторинг — обязателен.

## 4. Уровни доступа по статусу аттестации

| Статус | Доступ |
|--------|--------|
| Аттестован | Полный |
| Vendor временно недоступен, устройство было доверено ранее | Configurable grace не более 30 дней: текущая сессия и private send разрешены; новая регистрация и linking запрещены |
| Vendor недоступен, устройство ранее не подтверждено | Регистрация, linking и private send запрещены до успешной аттестации |
| Proof failed/forged (root/jailbreak-подделка, форк) | Полный отказ без grace; security event и отзыв сессии по policy |

Grace включается серверной policy только для `vendor_unavailable`; его нельзя применять к `proof_failed` или `proof_forged`. Истечение 30 дней блокирует чувствительные операции до новой успешной аттестации.
